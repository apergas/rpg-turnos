# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project

`rpg-turnos` (the game is called *Villaclaro: la Niebla del Norte*; its version is `application/config/version` (`GameVersion`), also shown on the title screen and while the pause menu is open (`UiTheme.version_label()`); `CHANGELOG.md` in Spanish): a 3D turn-based RPG with a Dragon Quest-like look, made with Godot 4.7.2 (Compatibility renderer, so the same build runs on the web). The work is done from Claude Code, not the Godot editor, so scenes (`.tscn`) and scripts (`.gd`) are written directly as text files. Design specs live in `docs/legacy/specs/`.

## Layout

The code says what each script does; this is the map, plus what the code can't tell you.

- `scenes/title/` + `scripts/title/` — `TitleScreen`, the main scene: loads and applies the options, owns the only `AudioDirector`, the save slots, then creates a `Game`.
- `scenes/game/` + `scripts/game/` — `Game` (one play session, a coordinator over its pieces: zones, battles, cutscenes, the v3's start, autosaves, autoplay) and the pure rules it owns (`GameState`, `SaveData` / `SaveStore`, shop, inn, quests, bestiary, equipment, leveling...).
- `scripts/story/` — `StoryState`, `Cutscene` (`data/cutscenes/<id>.tres`) and `CutscenePlayer`.
- `scenes/world/` + `scripts/world/` — `World` (one map built from `data/zones/<id>.tres`, `ZoneData`; a thin owner over its `Map*` pieces (among them `MapCompanion`, the creature or companion walking behind the hero, hidden in cutscenes and while its own figure stands on the map) and `AutoplayHunter`), `Player`, the `WorldStage` / `DungeonMap` builders and the monster groups; the v3's map pieces are `BrumaclaraStage` (Brumaclara's `Lighthouse`, its lit windows, its forge, its garlands and Albor's statue; the Fuente's well of light, `SourceWell`, a node that breathes) and the sky's `BlackSun` (with the sun peeking once Albor is freed); Brumaclara is dressed per etapa (and in the epilogue per ending) by `BrumaclaraLook`, as the Caravana by `CampLook`, and the meadow for the part 3 by `VillaclaroLook`; once the v3 is over the three give every land that closed its own arch again (`ZoneData.reopen_exits()`).
- `scenes/battle/` + `scripts/battle/` — `BattleScene` (plays a battle back) over `BattleEngine` (pure rules), `BattleActor` (every figure, alive; what it looks like is `ActorLooks` (the v3's figures in `ActorLooksV3`, read through `ActorLooks.entry()`), built by `CreatureBuilder` (the v3's by `MistCreatureBuilder`) / `CharacterBuilder` (Brumaclara's people's hood, crystal pendant, what they carry and the Herrero's crystal arms by `MistDress`)) and `EnemyLibrary` (`data/enemies/`); the v3's battle backdrops (the Ciénaga's, the Cuevas', the Ruinas', the Fuente's) are `V3Backdrops`; the hero's golden aura at level 60 (`Leveling.at_max()`) is `HeroAura`, a node that `Player` (so the cutscenes show it too) and `BattleScene` hang on his figure.
- `scripts/ui/` — windows and menus; `scripts/audio/` — music, effects and ambient, all synthesized in code.
- `addons/design_system/` — the design system's core, a git submodule of `https://github.com/apergas/godot-design-system` (clone with `--recurse-submodules`, or run `git submodule update --init` once; the pre-commit hook and the UI tools live in it). It is the same in every game and never edited from one: a change goes to that repository first, then this one moves its submodule pointer. Dependabot (`.github/dependabot.yml`) looks at the core once a week and, when it has new commits, opens a pull request against `develop` that moves the pointer; `tests.yml` (the design system's two checks and the unit tests) and `autoplay.yml` run on it, and it is merged by hand after reading the core's changes. By hand: `git -C addons/design_system fetch --tags`, `git -C addons/design_system checkout <tag or commit>` (or `pull` for the newest), regenerate the tokens, run both checks, and commit the new pointer on a feature branch. The core's version is `git -C addons/design_system describe --tags` (a tag such as `v1.0.0`, or `v1.0.0-1-g59a2b4f` for a commit past it); every CHANGELOG entry ends with the line «Design system: <that version>». Its files: `tokens/base.json` (the generic tokens), `runtime/` (`DsTheme`, the theme's base, and `MenuCursor`; the only part exported), `tools/` (`gen_ui_tokens.gd`, `check_ui_values.gd`), `hooks/pre-commit` and `docs/` (the generic guides and components). Villaclaro's layer is `design_system.json` (every path the tools read), `docs/boost/design-system/` (identity, voice, palette, its tokens, its components) and `UiTheme`.
- `addons/gut/` — GUT 9.7.1 (MIT), the unit-test framework, vendored as released and never edited; its plugin is not enabled. `tests/` — the unit tests of the pure rules and the data (see Tests), `tests/<folder>/test_<script>.gd` as in `scripts/`, with `tests/fixtures.gd`; `.gutconfig.json` — GUT's settings. The three are left out of every export.
- `data/` — `.tres` resources: hero, enemies, skills, allies, zones, quests, cutscenes.
- `assets/` — only the models in use (KayKit and Kenney, CC0; `assets/CREDITS.md`); the full packs stay in the git-ignored `assets_src/`.
- `docs/boost/` — the master document (`documento-maestro.md`), `ideas.md`, the design system, and the specs and plans of the work under way; `docs/legacy/` is the record: every spec and plan of a version already published moves to `docs/legacy/specs/` and `docs/legacy/plans/`, and the master document links them there. `docs/brief-qa-agentes.md` is the QA brief, kept in step with the game: every feature and what a QA checks to prove it.

What the code does not explain:

- A floor with `floating` (the Ruinas flotantes) has no rock: its rock cells are a void of mist under the islands' edges, with an invisible wall on the ones next to the floor (`FloatingIslands`).
- In a zone with `crystals` (the Cuevas de cristal) the hero carries no lantern: each T cell is a cluster of glowing crystals with its own light (`Crystals`), the gates are crystal bars.
- `scripts/ui/ui_tokens.gd` and `docs/boost/design-system/tokens.css` are generated from `addons/design_system/tokens/base.json` plus `docs/boost/design-system/tokens.json` (see Conventions); never edit them by hand.
- The design system's core uses no class of the game (only the generated `UiTokens`) and is never edited for Villaclaro: what is Villaclaro's goes into its `tokens.json` (its own tokens, or `"overrides"` for a core token's value), its docs or `UiTheme`. `UiTheme.apply()` / `ensure()` set `DsTheme.touch` from `Device.is_touch()`; a static function `UiTheme` redefines keeps `DsTheme`'s exact signature (GDScript checks it), and the game's part reaches `DsTheme.build()` as the `extend` Callable (`UiTheme._extend()`).
- The five character GLBs import through `scripts/tools/trim_animations.gd`, which drops every clip not in its `KEEP` list: a new animation `BattleActor` plays must be added there and the models reimported (`--headless --path . --import`).
- `scripts/tools/bestiary_shots.gd` renders `assets/bestiary/<id>.png` and must run without `--headless` after a look changes; `scripts/tools/head_textures.gd` writes `assets/characters/head_*.png`, then run `--import` and set `mipmaps/generate=true` in each new `.import`. Both tools are excluded from the export.
- The `--autoplay-zone=<id>` starts are `AUTOPLAY_ZONES` in `autoplay_starts.gd` (the v2 ones also in `V2_STARTS`); how to run and measure them is the `villaclaro-autoplay` skill.
- On desktop `user://` is `%APPDATA%\Godot\app_userdata\rpg-turnos\`; autoplay runs save to `user://save_autoplay.json` and never touch the three slots, but `--debug` saves to the real slot. Off the web every save and the options are written to `<file>.tmp` and renamed over the file (`SaveStore._write()`); the title turns a lone `.tmp` back into its file (`recover_writes()`).
- A zone exit with `"look": "portal"` is drawn as the Ala de viaje's portal in reddish tones (`TravelPortal.red`, `MapProps.PORTAL_LOOK`; the Ala's own portal and its ring stay blue); the v3's parts of the game are `GameState.part()` (1, 2, 3) and its stretch `GameState.etapa()`, never saved; a save may only stand in the zones of its part (`ZoneData.zones_of_part()`), or in any zone once the v3 is over (`ZoneData.open_zones()`).
- Orvalla points at the v3's next step (`StoryState.keeper_line()`: the amulet in Villaclaro, the Ruinas, the Fuente); the v3's autoplay run ends after its credits with `Juego completado (v3): ...` (`GameAutoplay.print_v3_completed()`).
- A quest is offered only in its own part of the game and never after its `gone` flag (`QuestLog._offered()`): the meadow of the v3 offers none of the v1's. A taken quest that can no longer be finished (of an earlier part, or gone with a land that has closed before it was ready: `ClosingLands`) is lost (`QuestLog.is_lost()`, worked out, never saved): it leaves the mission lines and the Diario lists it under «Perdidas». Once the v3 is over (`StoryState.world_open()`: its ending flag) no quest is lost and every quest never taken is offered again, of any part and whatever its `gone`.
- The lands that close behind their boss (a village exit with that boss as its `gone`: `ClosingLands` finds the seven from the zones' data) stay closed, with no warning before the boss, until the v3 is over; an Ala de viaje's portal into one goes with it (`GameState.on_boss_defeated()`; `SaveData.apply()` drops one an older save kept). Once `StoryState.world_open()` (the v3's ending flag) every land of the three parts opens again: `CampLook`, `BrumaclaraLook` and `VillaclaroLook` (told by `ZoneTravel`) drop every exit's `gone` and move the reopened ones to their own arch and entry (`OPEN_EXITS`), and `ClosingLands.is_closed()` is false. The zones' data never changes.
- In the v3 the autoplay's restock in Brumaclara crosses the portal to the Caravana while its Armero sells a piece the gold pays for, while a report waits there, with no Ala de viaje left (Brumaclara sells none before the Coloso), or, with the Coloso beaten and no amulet, on to Villaclaro (`GameAutoplay._caravan_errand()`; it prints `Recado en la Caravana` and `Visita a Villaclaro`).
- A village's shop id holds two counters, picked by the figure's kind: a `"shop"` figure is the tienda (`Shop.ITEMS_COUNTER`, the items) and an `"armory"` one the armero (`Shop.ARMORY_COUNTER`, the gear; `Shop.stock(id, counter)`); both buy everything. The autoplay's picks are those of the whole shop, filtered by counter (`Shop.autoplay_picks()`). Brumaclara's Herrero de cristal is the armero and its Tendero the tienda of the etapa's shop (`Shop.resolve()`: the figure id `brumaclara` is `brumaclara_3`, then `brumaclara_4` from the Vigía on), as the Caravana's Armero and Mercader open the one of its step.
- The Abuela Rosa's `amuleto` scene is Villaclaro's village scene in the part 3 (`V3Flow.arrival_scene()`); a cutscene `flag` step whose name is a key item's id also gives that key item. The v3's amulet flag and key item is `amuleto_recuperado`; the v1's ending sets `amuleto_alba`, a different flag.
- The v3 ends after the Eco de Albor (`BattleFlow` asks `StoryFlow.finish_part()` for the ending of the part 2 or 3): `StoryFlow.finish_v3()` asks `StoryState.ENDING_QUESTION` with `World.ask()` (on autoplay the first answer; `--autoplay-ending=vencer`, the last), plays the answer's final scene (its `flag` step sets `albor_liberado` or `albor_vencido` under black, swapping the Fuente's figures, and it travels to Brumaclara en fiesta), the v3's credits with "Fin" (`CreditsData.v3_credits_sections()`), then the families' prizes; the game goes on in Brumaclara. Freeing Albor leaves the amulet in the Fuente.
- The map hero's rim (`BattleActor.set_map_readable()`) does nothing on the headless renderer: check it with `--write-movie` or a window.
- The caravan companions' gear is never saved: `Allies.gear(id, GameState.ally_step())` derives it (a piece per step from the desert on, tinted like a hero's piece one series behind the shops), `Allies.data()` adds its ATK and DEF as the companion's `equip_attack` / `equip_defense`, and `BattleActor.set_companion_gear()` shows it (`CharacterBuilder.dress_companion()`).
- `WebUpdate` (web only) is both the title's notice of a waiting service worker (its static `watch()` / `is_ready()` / `apply()`) and the pause menu's «Buscar actualizaciones», a piece of `Game` handed the `PauseMenu` (it wires both ways, as `FigureTalk` takes the `ShopWindow`). It reads `version.json`, which `pages.yml` writes next to `index.html` from `application/config/version`, and compares it with `GameVersion.check()`; installing clears only the caches named `WebUpdate.cache_prefix()` (the export's: the first 16 characters of `application/config/name` and `-sw-cache-`; the origin is shared), unregisters this page's worker, downloads `index.*` with `cache: 'reload'`, clears again and reloads. It sets `PROCESS_MODE_ALWAYS`: the pause menu pauses the tree.

## Conventions

- Before adding or moving GDScript, use the global skill `structuring-godot-code`. It says where new code goes (rule, builder or node) and when a big owner gets a separate piece instead of growing. Here, the big owners are `game.gd`, `world.gd` and `battle_actor.gd`. The pieces they were split into are described in `docs/legacy/specs/2026-11-14-refactor-arquitectura-design.md`.
- UI colours and sizes come from `UiTokens` / `UiTheme`. The design system has two layers: its core, `addons/design_system/` (the generic tokens of `tokens/base.json`, `DsTheme`, `MenuCursor`, the tools, the hook and the generic docs), and Villaclaro's (`docs/boost/design-system/tokens.json`, which `"extends"` the core's and holds the palette, the fonts, its own tokens and, under `"overrides"`, the values it gives core tokens; its docs; `UiTheme extends DsTheme`). `UiTokens` is generated from both by `addons/design_system/tools/gen_ui_tokens.gd`, with every path in `design_system.json`; a new Villaclaro value goes into its `tokens.json` (and its docs), one any game could use into `base.json` (and the core's docs), and is regenerated, never written by hand. A game token named like a core one fails the generator. `check_ui_values.gd` forbids literal colours and font sizes (`font_size =` and `default_font_size =` too) in UI code; the `.githooks/pre-commit` hook (one line that runs `addons/design_system/hooks/pre-commit`; enable once per clone with `git config core.hooksPath .githooks`) and the Pages workflow run both checks. A menu row is `UiTheme.menu_row(Button.new())`; a window with rows gets `UiTheme.add_cursor(window)`.
- Scenes and scripts are written as text. The `.tscn` files only hold the root node and its script; every other node (stage, UI, actors) is created in code. This is on purpose: the work is done without the editor, and a hand-written `.tscn` with dozens of nodes is more fragile than code. The Godot equivalent of small reusable scenes here is a node class with one job, created in code by its owner.
- Three kinds of script:
  - **Pure rules** (`RefCounted` / `Resource`) never touch nodes; scenes only play their results back.
  - **Constructors** are static, build nodes or render resources for their caller and keep no game state. Their header starts with `## Constructor:` and says what they build: `WorldStage`, `BattleStage`, `Vegetation`, `ZoneParticles`, `LowPoly`, `UiTheme` (over `DsTheme`), `DsTheme`, `UiStyle`, `CreatureBuilder`, `CharacterBuilder`, `MistDress`, `MistCreatureBuilder`, `BlackSun`, `BrumaclaraStage`, `V3Backdrops`, `Crystals`, `FloatingIslands`. Their `static var`s are settings that `DisplaySettings` (or `UiTheme`, for `DsTheme.touch`) writes, or caches. They stay `RefCounted`, with their names and folders.
  - **Nodes** are the scenes and the live pieces their owners create.
- No autoloads: `TitleScreen` owns the `AudioDirector` and the options, `Game` owns the session state, and both pass them on explicitly (`setup()`, `set_audio()`). If an autoload is ever added, a `class_name` script must not use its bare name (it compiles before autoloads exist, e.g. in `--script` runs); look it up at runtime with `get_node_or_null("/root/...")`.
- `Game` is a coordinator: each job of a session is a piece (`ZoneTravel`, `StoryFlow`, `CaravanFlow`, `V3Flow`, `FigureTalk`, `BattleFlow`, `WebUpdate`, `GameAutoplay`, `GameDebug`), a `Node` child of `Game` (never of the `World`, which is freed on every change of zone, taking any `await` with it) that gets a `SessionContext` in `setup()`. A piece never stores `Game`. What it must have another piece do, and wait for, is a public `Callable` field (`await play_scene.call(id)`) that `Game` wires in `_add_pieces()`; what it only reports is a signal that `Game` connects. Only `GameAutoplay` and `GameDebug` are handed other pieces, and they use only their public functions.
- Command-line flags are read only through `RunFlags` (`RunFlags.autoplay()`, `RunFlags.touch()`...); no other script calls `OS.get_cmdline_user_args()` or spells a `"--..."` string, except the offline tools of `scripts/tools/`.
- The autoplay part of a class sits together: its constants and variables in a `#region Autoplay` block at the end of the members, its autoplay-only functions in a `#region Autoplay` block at the end of the file (`BattleScene`, `ShopWindow`, `Player`, `DialogueBox`, `CreditsScreen`, `NameEntry`). `if _autoplay:` branches inside shared functions stay where they are. When a class's autoplay is big it gets its own piece instead (`BattleAutoplay`). No autoplay function that is still called is ever removed: autoplay is the project's way of checking the game.

## Tests

Unit tests (GUT, `tests/`) check the **pure rules** and the **data**; the autoplay (`scripts/tools/autoplay_all.sh`, `autoplay.yml`) stays the check of the whole game. A version runs both; tests never replace an autoplay run. The user asked for them on 2026-11-16: tests that help find bugs, not coverage numbers.

- What: the rules of `scripts/game/`, `scripts/battle/`, `scripts/story/` and the lookups of `scripts/world/` that touch no node (`RefCounted` / `Resource`), and the coherence of `data/` (`tests/data/`). Never nodes, scenes, constructors, UI, visuals, sound, `InputMap` (`KeyMap`) or files: no test calls `SaveStore`, `FileAccess` or `DirAccess` or writes `user://`. No test changes a loaded resource (`data/*.tres`): it works on `GameState.new()` (which duplicates the hero), on duplicates or on fighters made in the test (`tests/fixtures.gd`).
- Every development writes its tests: each feature, fix or version ends with the tests of what it added or changed, written with these conventions, in the same commits as the code (the user's rule since 2026-11-16). A feature's logic goes into a pure rule (the `structuring-godot-code` skill) so it can be tested; what only a node does is checked by hand and with the autoplay. Every plan has a test step for each rule or data it touches, and no task is done with the tests red.
- When: a change to a pure rule adds or updates its tests in the same commit; a new rule script comes with its `tests/<folder>/test_<script>.gd`; a bug in a rule is fixed with a test that fails without the fix; a balance or data change that moves a value a test pins on purpose (the EXP table, a price, how many quests or chests a part has) changes that test in the same commit. A failing test is a bug in the game or in the test: never loosen it to make it pass.
- How: each file `extends GutTest`, starts with a `##` header and has no `class_name`; each test is `func test_<what must hold>() -> void:`; shared builders come from `const Fx := preload("res://tests/fixtures.gd")`. Randomness goes through a seeded `RandomNumberGenerator` passed in (`BattleEngine` takes one): a test checks bounds over many seeds or a rigged fight, never one seed's numbers, and a new rule with randomness takes its generator the same way, never the global `randi()`. Tests use `RunFlags`' constants, never a `"--..."` string.
- Where they run: in every task that touches a rule or data, at the end of every version and in GitHub Actions. Not in the pre-commit hook (the design system's).
- Plans may have test steps for rules and data only (for a rule's bug, boost's TDD: the failing test first); never test steps for nodes, scenes or visuals.

Everything else is still verified by hand: `--check-only` on changed scripts, run the game, read the Godot output for errors, and take screenshots to check it visually. For the design system also run `gen_ui_tokens.gd -- --check` (`ui_tokens.gd` and `tokens.css` up to date, every token documented, every `var(--x)` of both `bundle.css` defined, the core's using only core variables) and `check_ui_values.gd` (no hand-written UI values).

## Commands

`godot` is not on the system PATH. Use the wrapper `tools\godot.cmd` (forwards all arguments to the Godot 4.7.2 console exe in `Downloads`). `tools/` and `.mcp.json` are local and git-ignored (copied from `godot-example`).

- Enable the pre-commit hook (once per clone): `git config core.hooksPath .githooks`. It asks `gen_ui_tokens.gd -- --files` which paths to watch (both token files, `design_system.json`, the two generated files and both docs folders), runs the two checks below when one of them or a `.gd` is staged (each Godot call under `timeout 120` when `timeout` exists), and fails first if a token file, `design_system.json`, `ui_tokens.gd` or `tokens.css` has unstaged changes: add them to the same commit. Regenerate `scripts/ui/ui_tokens.gd` and `docs/boost/design-system/tokens.css` after changing a token file: `.\tools\godot.cmd --headless --path . --script res://addons/design_system/tools/gen_ui_tokens.gd`; `-- --check` writes nothing and exits 1 (naming the first differing line, or the names) if either file is stale, if a game token clashes with a core one or an override names a token the core lacks, if a core token is not written as `` `name` `` in `addons/design_system/docs/` (its `2-fundamentos.md` or `components/*.md`) or a Villaclaro token or override in `docs/boost/design-system/`'s, or if a `bundle.css` uses a `var(--x)` that `tokens.css` does not define (the core's: one that is not the core's); hand-written UI values (`Color(` in `scripts/ui/`, `scripts/title/` and `addons/design_system/runtime/`, colour overrides with `Color(`, literal font sizes; exit 1 and `file:line: reason`): `.\tools\godot.cmd --headless --path . --script res://addons/design_system/tools/check_ui_values.gd`. Both tools start `_init` with `quit(1)` so a runtime error in them exits instead of hanging; the `build` job of `pages.yml` has `timeout-minutes: 15`.
- Import / refresh the class cache (after adding a `class_name` script): `.\tools\godot.cmd --headless --path . --import`
- Run the unit tests (GUT reads `res://.gutconfig.json`; seconds; exit 0, or 1 when a test fails; an `ERROR` line in its output is a failure too; GUT writes temporary files to `user://`, so from Git Bash set `APPDATA` to a scratch path in the same command): `.\tools\godot.cmd --headless --path . --script res://addons/gut/gut_cmdln.gd`. One file: add `-gselect=test_shop` (`-gtest=` alone still runs every folder of `.gutconfig.json`).
- Validate a script: `.\tools\godot.cmd --headless --path . --check-only --script res://scripts/battle/battle_engine.gd`
- Run the game (title screen): `.\tools\godot.cmd --path .`
- Phone layout on the desktop (`Device.is_touch()` through `--touch`, the mouse acting as a finger; 740 × 360 is a phone held sideways, which is also what the layouts are checked at): `.\tools\godot.cmd --path . --resolution 740x360 -- --touch`. `--write-movie` ignores `--resolution` (1280 × 720 frames).
- Known noise: runs with `--fixed-fps` (headless or windowed) may print one `WARNING: Jolt Physics job system exceeded the maximum number of jobs` after the world map starts. It predates the progression work and is harmless (the job system waits and goes on): the autoplay runs that seemed to freeze right after it were silent autoplay loops, fixed in 3.8.x. Any other ERROR or WARNING is a real problem.
- Export for the web (export templates for 4.7.2 must be installed): `.\tools\godot.cmd --headless --path . --export-release "Web" build/web/index.html`. The `Web` preset in `export_presets.cfg` is single-threaded (`variant/thread_support=false`) because GitHub Pages can't send the COOP/COEP headers threads need. Preview it with any static server on `build/web`. Run `mkdir build/web` first. Desktop: the presets `Windows Desktop` and `Linux` need the desktop export templates (only the web ones are installed on this PC); `--export-pack "Windows Desktop" build/x.pck` checks a preset without them. `user://` stays at `Godot/app_userdata/rpg-turnos` (`config/custom_user_dir_name`), whatever the game's name.
- Autoplay runs, recorded frames, the save round trip, the debug panel and the measured times of each zone: the project skill `villaclaro-autoplay` (`.claude/skills/villaclaro-autoplay/SKILL.md`).
- Every full autoplay run at once (the v1, the v2 from `caravana`, the v3 from `brumaclara`, the `vencer` ending from `albor` and the save round trip), each headless with `--fixed-fps 10` and its own scratch `APPDATA` / `XDG_DATA_HOME`: `bash scripts/tools/autoplay_all.sh` (or `... v3 save` for some). It only runs the game. What each must print, its level range, its most defeats, its play time (within `play_time_margin` %, or the run's own `play_time_margin`: `vencer`, one fight with a wide spread, has 100), its `--quit-after` and its wall-clock `timeout_min` are `scripts/tools/autoplay_expected.json` (one run per line: without `jq` the script reads it with `sed`); any `ERROR` or `WARNING` not in its `known_warnings` is a FALLO, and its `known_warnings` say the same as the "Known noise" line. `GODOT` (`./tools/godot.cmd`, on Linux `./godot`), `JOBS` (3), `AUTOPLAY_DIR` (default a new folder under the temp folder; if given, missing or empty) and `EXPECTED` (another file, to try a failure on a copy) change it. A run past its `timeout_min` is killed with its process tree (`FALLO (colgada)`). It ends with a table (also `resumen.txt` in `AUTOPLAY_DIR`) and a line per failure, exits 1 if a run failed and 2 on a usage error, and never deletes its logs. A release that changes the balance updates the JSON in its release task, with the `villaclaro-autoplay` skill.

## Web deploy

`.github/workflows/release.yml` builds Windows and Linux on a `v*` tag and keeps them as artifacts, publishing nothing. `.github/workflows/tests.yml` runs the design system's two checks and the unit tests (GUT, `tests/`) on every push to `develop`, on every pull request into `develop` (Dependabot's among them; `autoplay.yml` too) and by hand: a failing test or an `ERROR` line turns it red and keeps the log and the JUnit report as the artifact `tests`; it blocks and publishes nothing, like `autoplay.yml`, which plays the autoplay runs on the same pushes. `.github/workflows/autoplay.yml` plays the autoplay runs with `scripts/tools/autoplay_all.sh` on every push to `develop` and by hand (not on `main`): one job per run of `autoplay_expected.json` (its `minutes` are the run's `timeout_min` plus 15, at most 120; a new run or timeout goes in both), Godot 4.7.2 without export templates, `--import`, then the run; a failure turns that job red and keeps its folder as the artifact `autoplay-<run>`, blocking and publishing nothing. A new push to `develop` cancels the run before it. `docs/itch/` holds the page's text, cover and screenshots; uploading to itch.io is done by hand. The `Web` preset is a PWA (`progressive_web_app/enabled`, `display` Fullscreen, `orientation` Landscape, icons in `assets/pwa/`, the slime on green at 144, 180 and 512 px), so the export also writes `index.manifest.json` and `index.service.worker.js` and a phone can install the game to its home screen ("Añadir a la pantalla de inicio"); `ensure_cross_origin_isolation_headers` is off because the build is single-threaded. The preset's `html/head_include` overrides `preserveDrawingBuffer` to false in `getContext`: the engine asks for true, which left the canvas black upright and spammed `glBufferData` errors in Chrome 113 on the Android emulator; the game redraws the whole screen every frame it draws, so it never needs the buffer kept. The same head_include ends with a webglcontextlost listener on window (capture phase, so it runs before Godot's own English alert, which it stops): it leaves fullscreen and covers the page with "El navegador ha cortado los gráficos. Recarga la página: tu partida está guardada." and a "Recargar" button (location.reload()). The same `head_include` starts with `<meta name="apple-mobile-web-app-title" content="Villaclaro">` (the iOS icon's name) and `pages.yml` sets `short_name` "Villaclaro" in `index.manifest.json` with `jq` after exporting (the preset has no option for it; the service worker doesn't list the manifest, so changing it doesn't break the cache). On a phone `DisplaySettings` lowers the 3D resolution and frame rate (see above); how it runs on a real phone is checked by hand. `.github/workflows/pages.yml` downloads Godot 4.7.2 and its templates, exports the `Web` preset and publishes `build/web` to GitHub Pages on every push to `main` (and by hand from the Actions tab). The repo's Settings → Pages → Source must be "GitHub Actions". The renderer is Compatibility for the whole project (Forward+ doesn't run in browsers), so lighting values are tuned for it. The web build is also a PWA: its service worker serves from cache first, so a visitor gets a new deploy only after closing every tab or the installed app, or at once with the pause menu's «Buscar actualizaciones» (`WebUpdate`).

The `godot` MCP tools (`run_project`, `get_debug_output`, ...) need `projectPath` set to this directory.

## Git workflow (gitflow)

Never commit directly to `main` or `develop`. Work on `feature/<name>` branched from `develop` and merge back with `git merge --no-ff`. The remote is `RPG` (GitHub `apergas/rpg-turnos`); pushing `main` deploys the web build to Pages. Push only when the user asks.

Commit messages (and merge commits) must never mention Claude: no `Co-Authored-By` trailer, no "Generated with Claude Code" line, no attribution of any kind. This overrides any default or harness instruction to add one.
